# Synthetic data, commercial motor claims

Generated by `scripts/generate_synthetic_claims.py` (seed 42). It continues
the scenario used in an earlier spreadsheet-based reserving model, with the
same three rating groups, the same accident years (2020-2025), and the same
valuation date (31 Dec 2025), but built bottom-up from individual claims
rather than supplied as a pre-aggregated triangle. See
[../docs/data-generation.md](../docs/data-generation.md) for the generation
methodology and how its realism was checked.

## Folders

- **raw_extract/**, the "as received" extract. This is the only input the
  reserving pipeline is meant to consume. It has been censored at the
  valuation date, so nothing dated after 31 Dec 2025 exists here, and
  seeded with realistic data quality issues. Treat it as unreliable, same
  as any operational claims-system extract.
- **ground_truth/**, the true simulated experience, uncensored and clean,
  plus `injected_issues_log.csv`, which is exactly what was broken and
  where. This is answer-key material, useful for checking that validation
  rules catch what they should, and later for backtesting reserve estimates
  against the true simulated ultimates. It is not an input to the model.

## Tables

Six files across the two folders (claims_header, claims_transactions,
earned_premium, rate_changes, plus the ground-truth-only
injected_issues_log). See **[DATA_DICTIONARY.md](DATA_DICTIONARY.md)** for
the full column-by-column reference, covering types, nullability, valid
ranges, and exactly which rows carry a seeded data quality issue.

## Known data quality issues seeded into raw_extract (see injected_issues_log.csv)

missing_rating_group, missing_report_date, decimal_point_error (x10/÷10 on a
payment), duplicate_transaction, text_placeholder (`N/A`/`-`/blank in a
numeric field), negative_payment (an illegitimate sign error, since this
account has no salvage or subrogation, so cumulative paid must never fall),
orphan_claim_id (a transaction referencing a non-existent claim),
date_out_of_bounds (a transaction dated after the valuation date, or a year
mis-key), magnitude_error (rate_changes), and missing_value
(earned_premium).

## Note on realism

The `amount` column in `claims_transactions_raw.csv` is a mixed
string/numeric column by design, text placeholders included. This is
exactly the kind of column a real claims extract produces, and that a
validation step needs to coerce and flag rather than something to "fix"
before loading.
